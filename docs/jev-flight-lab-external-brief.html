1. What the product is

JEV Flight Lab is a Flappy Bird–style 2D browser demo. A neon drone flies through gate openings. The game engine owns physics, rendering, collisions, and scoring. Jev is not the game — it is a tactical decision service that only answers FLAP or WAIT.

Game state → bounded AI decision → action → observable outcome

The demo shows a real-time control loop with a typed decision model, not chat-based “play the game with prose.”

2. Architecture — who owns what

Layer Owns Does not own
Game engine Physics, gates, collisions, score, lifecycle AI reasoning
Harness (DecisionManager) Cadence, timeout, stale checks, fallback, apply/discard Model weights
Jev provider Projects state, calls API, parses choice Execution in the world
Optional LLM analyst Slow strategic commentary (~10s) Per-tick control

Critical split: Jev decides; the harness decides whether that answer is still safe to apply; the engine applies a single physics impulse if allowed.

3. End-to-end control loop

Animation frame (~60fps)
  → engine.update(physics)
  → build TacticalState from live pose
  → DecisionManager.sync(session, state)
  → maybeRequest() if interval elapsed & no in-flight call
       → project state by ~latency lead
       → POST /api/jev/decision  { state }
       → server builds Decisions API payload (prompts + telemetry)
       → OpenRouter Jev returns choice flap|wait
  → harness validates age / relevance / session
  → if flap + autopilot + still valid → engine.dispatch(FLAP)
       → velocityY = flapImpulse (one bounded hop)
  → if wait → do nothing (gravity continues)

Cadence is adaptive (~40–100 ms target poll), but only one request is in flight, so real rate is bounded by network RTT. Client timeout: 1 s. Max decision age: 1 s.

4. Input state (what we send toward Jev)

Flow: browser posts projected telemetry to POST /api/jev/decision → server wraps it with prompts → OpenRouter Decisions API. Telemetry is a projected snapshot (lead ≈ recent latency, ~200–1000 ms) so Jev answers for near-future pose, not already-stale past.

5. Jev prompts (exact strings from the app)

Jev uses the Decisions API, not chat completions. There is no free-form system chat prompt. The “prompt” is the structured state.* strings plus questions.action below (source: buildJevDecisionsRequest, forecastIfWaiting, describeFlapAgainstOpening).

5.1 Fixed task

state.task

Fly the drone through the gate openings. ifYouWait says where the drone is and where one more WAIT leaves it. Do not add any further prediction.

5.2 Generated situation strings

These are rebuilt every request from the live/projected TacticalState. Templates (placeholders filled at runtime):

state.ifYouWait — from forecastIfWaiting()

If you WAIT, the drone is {placePhrase(relativeGapOffset)}, {close to the floor | clear of the floor | close to the ceiling}, and {falling | rising | level}. The gate arrives in {seconds}s. One more WAIT leaves the drone {below | inside | above} the opening. With no flap, the engine predicts {placePhrase(predictedOffsetAtGate)} at the gate.

state.oneFlap — from describeFlapAgainstOpening()

One FLAP climbs about {climbPx}px. The next opening extends {halfGap}px above and below its center. Compared with this hurdle, that climb {would carry the drone above the opening | covers the Npx below the center and still leaves the drone inside the opening | would move the drone farther above the center}. WAIT lets gravity pull the drone down.

Example after filling:

"ifYouWait": "If you WAIT, the drone is 18px below the opening center, clear of the floor, and falling. The gate arrives in 0.9s. One more WAIT leaves the drone below the opening. With no flap, the engine predicts 34px below the opening center at the gate.",
"oneFlap": "One FLAP climbs about 48px. The next opening extends 84px above and below its center. Compared with this hurdle, that climb covers the 18px below the center and still leaves the drone inside the opening. WAIT lets gravity pull the drone down."

5.3 Choice question — instructions

questions.action.instructions

Use ifYouWait and oneFlap only. Compare the FLAP climb with the opening height. FLAP when the drone is below the opening center and that climb still leaves it inside the opening, or one more WAIT leaves it below the opening, or it is close to the floor. WAIT when that climb would carry the drone above the opening, or the drone is already on or above the opening center and one more WAIT leaves it inside or above the opening, and it is clear of the floor. FLAP never moves the drone downward.

5.4 Choice criteria

questions.action.criteria.flap

The drone is below the opening center and one FLAP still leaves it inside the opening, or one more WAIT leaves it below the opening, or it is close to the floor.

questions.action.criteria.wait

One FLAP would carry the drone above the opening, or the drone is on or above the opening center and one more WAIT leaves it inside or above the opening, and it is clear of the floor.

The ask: return a typed choice — flap or wait — under those criteria. Jev is not asked for prose explanations.

6.3 Failure / backup output

On timeout, HTTP error, or invalid choice, the harness calls a backup (local model or deterministic heuristic). That output still has action: "flap" | "wait", but provider is "local" or "fallback" (never relabeled as live Jev).

7. How the agent executes the output

Answer Execution
wait No control action; gravity keeps acting
flap If still valid under harness rules → FLAP → sets velocityY = flapImpulse once

The harness may discard even a “correct” Jev flap when:

  • decision age > 1 s (too_old)
  • drone already above the opening enough that a flap would climb into the pipe (above_opening)
  • a second impulse too soon after another flap (second_flap, ~280 ms quiet window)
  • response belongs to a previous flight/session (previous_flight / replaced)

Model output ≠ world action. The harness is the safety / relevance gate.

8. Key limitations and challenges

  • Latency vs game speed. Gates close in seconds; Jev RTT is often hundreds of ms. Mitigation: state projection + stale discard — projection is approximate, not a full simulator inside Jev.
  • Binary, myopic action space. Only flap/wait for the current opening. No multi-gate planning, thrust magnitude, or continuous control.
  • Prompted heuristics in the loop. ifYouWait / oneFlap / criteria are app-authored summaries. Results partly reflect prompt engineering, not raw pixel perception.
  • No visual perception. Jev never sees the canvas — only derived numbers + natural language. Feature extraction errors become model errors.
  • Fallback opacity vs truthfulness. Timeouts use heuristic/local backup so the drone keeps flying. UI must label fallback, or demos overclaim “Jev flew.”
  • Non-determinism and eval hardness. Same state can yield different choices; live score is a noisy KPI. Replay/benchmark tooling helps.
  • Stale-discard tradeoff. Aggressive discard avoids late ceiling flaps, but throws away expensive answers and can under-control under high latency.
  • Scope boundary. This is a lab demo of structured real-time decisions — not production autonomy or sim-to-real transfer.

9. Stakeholder summary

We run a tiny real-time flight sim; every few dozen milliseconds a harness asks Jev “flap or wait?” with projected telemetry and fixed criteria; Jev returns a typed choice; the harness only applies flaps that are still relevant to the live pose, otherwise falls back or waits — making the demo about bounded, inspectable decision latency, not open-ended LLM gameplay.
